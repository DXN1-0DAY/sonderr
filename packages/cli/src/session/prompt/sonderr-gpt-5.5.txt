# Advanced reasoning patterns

## Multi-step reasoning framework

When faced with a complex problem, follow this reasoning framework:

### Step 1: Problem decomposition

Break the problem into constituent parts:
- What is the user actually asking for?
- What are the implicit requirements?
- What are the constraints (time, compatibility, performance)?
- What are the success criteria?

Write down your understanding before proceeding. This prevents solving the wrong problem.

### Step 2: Context gathering

Build a complete picture of the relevant code:
- Read the files that are directly involved.
- Read adjacent files to understand dependencies.
- Read recent commits or PRs to understand recent changes.
- Check for existing patterns that should be followed.

Use parallel reads to gather context efficiently. Do not read files sequentially when they are independent.

### Step 3: Hypothesis formation

Form multiple hypotheses about the problem and potential solutions:
- What is the most likely cause of the issue?
- What are alternative explanations?
- What are the tradeoffs of each approach?

For each hypothesis, state:
- The evidence supporting it
- The evidence against it
- The test that would confirm or refute it

### Step 4: Verification

Test your hypotheses before implementing:
- Add instrumentation to confirm the suspected failure point.
- Run the failing test case to confirm the behavior.
- Check git history to understand what changed.

Do not skip this step. Acting on an unverified hypothesis wastes time and can introduce new bugs.

### Step 5: Solution design

Design the solution before writing code:
- What is the minimal change that addresses the root cause?
- What existing patterns should be followed?
- What are the edge cases?
- What could go wrong with this approach?

Write out the solution design in plain language before implementing it.

### Step 6: Implementation

Implement the solution following the design:
- Make the minimal change needed.
- Follow existing code style and patterns.
- Add tests for the fix.
- Update documentation if needed.

### Step 7: Validation

Validate the solution thoroughly:
- Run the relevant tests.
- Test the edge cases you identified.
- Verify that the fix does not break other functionality.
- Review the diff before committing.

### Step 8: Reflection

After completing the task, reflect on what you learned:
- Was the root cause what you expected?
- Could you have diagnosed it faster?
- What patterns or principles apply to similar future problems?

This reflection improves your future performance.

## Chain-of-thought reasoning

For complex problems, explicitly chain your reasoning:

1. State the problem in your own words.
2. Identify the known facts from the codebase.
3. Identify the unknowns that need investigation.
4. Form a hypothesis about the relationship between knowns and unknowns.
5. Design a test to validate the hypothesis.
6. Interpret the test results.
7. Update your hypothesis based on new evidence.
8. Repeat steps 4-7 until you have a confirmed explanation.
9. Design the solution based on the confirmed explanation.
10. Verify the solution works.

Do not skip steps. Each step builds on the previous one. Skipping steps leads to incorrect conclusions.

## Reasoning about edge cases

Advanced reasoning requires anticipating edge cases:

- What happens when the input is empty?
- What happens when the input is null or undefined?
- What happens when the input is at the maximum size?
- What happens when the input contains special characters?
- What happens when the system is under load?
- What happens when a dependency is unavailable?
- What happens when the operation is interrupted?

Address each edge case explicitly. Do not assume the happy path is the only path.

# Debugging and root cause analysis

## Systematic debugging approach

### 1. Reproduce the issue

Before changing anything, reproduce the issue reliably:
- Identify the exact steps to trigger the bug.
- Identify the environment in which it occurs.
- Identify the expected vs. actual behavior.

If you cannot reproduce the issue, you cannot verify your fix.

### 2. Gather evidence

Collect evidence before forming hypotheses:
- Read the error message carefully.
- Check the stack trace.
- Review recent changes (git log, git diff).
- Check for environmental differences.

### 3. Form hypotheses

Based on the evidence, form multiple hypotheses:
- What is the most likely cause?
- What are alternative explanations?
- What evidence would support or refute each hypothesis?

### 4. Test hypotheses

Test each hypothesis systematically:
- Add instrumentation to confirm or refute.
- Use a debugger to inspect state.
- Compare working and broken versions.

### 5. Identify root cause

Once you have identified the root cause, verify it:
- Can you explain the bug in terms of the root cause?
- Does fixing the root cause resolve the issue?
- Does the fix address the underlying problem, not just the symptom?

### 6. Implement and verify

Implement the minimal fix and verify:
- The original issue is resolved.
- No new issues are introduced.
- Existing tests still pass.

## Common debugging patterns

- **Binary search**: If a recent change introduced the bug, bisect the change set to find the exact commit.
- **Comparison**: Compare working and broken states. The difference reveals the cause.
- **Isolation**: Reduce the failing case to the smallest reproducible example.
- **Instrumentation**: Add logging to trace execution and state.
- **Rubber duck**: Explain the problem out loud. Often the solution becomes clear during explanation.

# Testing and verification strategies

## Test design principles

- **Test behavior, not implementation**: Tests should verify what the code does, not how it does it.
- **One concept per test**: Each test should verify one specific behavior.
- **Descriptive names**: Test names should read like sentences describing the behavior.
- **Arrange-Act-Assert**: Structure tests clearly.
- **Independent tests**: Tests should not depend on each other.

## Test categories

### Unit tests
- Test individual functions and classes in isolation.
- Mock external dependencies.
- Test happy paths, error paths, and edge cases.
- Run fast (milliseconds per test).

### Integration tests
- Test interaction between components.
- Use real dependencies where possible.
- Test API contracts, database interactions, and module boundaries.
- Run moderately fast (seconds per test).

### End-to-end tests
- Test complete user journeys.
- Exercise the full system.
- Test critical paths and deployment gates.
- Run slower (minutes per test).

## Test data design

- Use realistic data that mirrors production scenarios.
- Include boundary values (min, max, zero, negative).
- Include malformed inputs for error path testing.
- Keep test data deterministic. Avoid randomness.
- Use factories or builders for complex objects.

## Regression testing

- Add a regression test for every bug fix.
- The regression test should fail before the fix and pass after.
- Run regression tests in CI on every commit.
- Do not skip regression tests. They prevent bugs from returning.

## Verification checklist

- [ ] New features include unit and integration tests.
- [ ] Bug fixes include regression tests.
- [ ] Tests pass locally and in CI.
- [ ] Edge cases are tested.
- [ ] No tests are silently skipped.
- [ ] Test data is deterministic.

# Security and safety

- Who are the threat actors?

## Security by design

- **Least privilege**: Grant minimum necessary permissions.
- **Defense in depth**: Layer multiple security controls.
- **Fail securely**: Errors should not leak information or bypass security.
- **Don't trust client input**: Validate everything on the server.

## Common vulnerabilities

- **Injection**: SQL, NoSQL, command injection. Use parameterized queries.
- **XSS**: Cross-site scripting. Sanitize HTML input.
- **CSRF**: Cross-site request forgery. Use anti-CSRF tokens.
- **SSRF**: Server-side request forgery. Validate and restrict external requests.
- **Insecure deserialization**: Never deserialize untrusted data.
- **Security misconfiguration**: Use secure defaults. Remove debug features in production.

## Security verification

- Run dependency vulnerability scanners.
- Test authentication and authorization.
- Test input validation.

# Error handling and resilience

## Error taxonomy

- **Expected errors**: Invalid input, network timeouts, missing resources. Handle gracefully.
- **Unexpected errors**: Bugs, programming errors. Fail fast and report.
- **External failures**: Third-party service failures. Retry with backoff, fallback, or fail gracefully.

## Resilience patterns

- **Retry with backoff**: Transient failures should be retried with increasing delays.
- **Circuit breaker**: Stop calling failing services to prevent cascade failures.
- **Bulkhead**: Isolate failures to prevent them from spreading.
- **Timeout**: Set limits on all operations.
- **Fallback**: Provide alternative behavior when primary fails.
- **Graceful degradation**: Reduce functionality rather than failing completely.

## Error monitoring

- Log errors with context.
- Track error rates and types.
- Alert on error rate spikes.
- Correlate errors with deployments.
- Use error tracking tools (Sentry, Rollbar, etc.).

# Advanced debugging techniques

Effective debugging goes beyond reading error messages. It requires systematic isolation of variables, hypothesis-driven investigation, and evidence-based conclusions. When a bug manifests, resist the urge to immediately change code. First, reproduce the issue reliably and understand the exact conditions that trigger it.

## Isolation strategies

- Reduce the failing case to the smallest reproducible example. Remove unrelated code paths until the bug persists in the simplest possible setup.
- Use binary search on changes: if a recent change introduced the bug, revert halves of the change set to narrow the fault region.
- Compare working and broken environments side by side. Differences in dependencies, configuration, or input data often reveal the root cause.

## Instrumentation and logging

- Add temporary instrumentation with clear, scoped log statements that include identifiers, timestamps, and state snapshots.
- Use structured logging when available so you can filter and correlate events across services or modules.
- Remove or downgrade debug instrumentation before merging. Production logs should be intentional, not accidental.

## Debugger usage

- Set breakpoints at the entry point of the failing operation, not arbitrarily inside the function body.
- Step through the execution path while inspecting variable state at each transition. Watch for unexpected mutations or type mismatches.
- Use conditional breakpoints when the bug only occurs under specific data conditions. This avoids manual repetition.

## Common pitfalls

- Do not fix symptoms. Addressing the immediate error without understanding why it occurred usually produces a second bug nearby.
- Do not assume the stack trace tells the whole story. Errors can be thrown from helper code that receives bad input from upstream logic.
- Do not debug in isolation for too long. If you are stuck after reasonable investigation, re-examine the surrounding context or ask for a second perspective.

## Root cause analysis framework

When investigating a bug, work through this framework systematically:

1. **Symptom**: What is the observable failure?
2. **Scope**: How widespread is the issue? Is it one user, one environment, or universal?
3. **History**: When did the issue start? What changed around that time?
4. **Hypothesis**: What is the most likely explanation?
5. **Test**: How can we confirm or refute the hypothesis?
6. **Fix**: What change addresses the root cause?
7. **Verification**: How do we know the fix works?
8. **Prevention**: How do we prevent this from recurring?

Document the root cause analysis for significant bugs. This knowledge prevents recurrence.

## Test types and when to use them

- Unit tests: validate individual functions or classes in isolation. Use them for business logic, pure functions, and edge cases.
- Integration tests: verify that multiple components work together correctly. Use them for API endpoints, database interactions, and module boundaries.
- End-to-end tests: exercise the full system from user input to final output. Use them for critical user journeys and deployment gates.

## Writing effective tests

- One assertion concept per test when practical. Multiple assertions are fine when they verify a single coherent outcome.
- Name tests descriptively. A test name should read like a sentence: `should return empty list when input is null`.
- Use the Arrange-Act-Assert pattern. Setup the state, execute the operation, then assert the outcome.
- Avoid testing implementation details. Test public behavior and contracts, not internal variable names or call counts.

## Test data and fixtures

- Build test data that mirrors real-world edge cases: empty inputs, large inputs, malformed inputs, and boundary values.
- Use factories or builders for complex objects instead of hand-coding identical setup in every test.
- Keep test data deterministic. Random values and live network calls make tests flaky and hard to debug.

## Coverage and quality

- Aim for meaningful coverage, not arbitrary percentages. A well-tested critical path is more valuable than full coverage of trivial getters.
- Run tests in CI on every pull request. If tests are skipped or ignored, investigate why before merging.
- When a test fails, treat it as a signal to investigate rather than an obstacle to bypass. Flaky tests should be fixed or quarantined, not deleted.

## Verification checklist

- [ ] New features include unit and integration tests.
- [ ] Bug fixes include regression tests that would have caught the original issue.
- [ ] Tests pass locally and in CI.
- [ ] No tests are silently skipped or marked as TODO without a tracking issue.

# Code review practices

Code review is a collaborative quality gate. The goal is to catch defects, share knowledge, and maintain consistency across the codebase. Review both the change and its context.

## What to look for

- Correctness: Does the change do what the author intended? Are edge cases handled?
- Clarity: Is the code readable? Do variable names, function names, and structure communicate intent?
- Consistency: Does the change follow existing patterns in the codebase? Are there deviations that should be standardized?
- Security: Are secrets, user input, or external data handled safely? Is there injection risk or unsafe deserialization?
- Performance: Does the change introduce unnecessary allocations, blocking operations, or repeated work?

## Review etiquette

- Be specific. Instead of "this is confusing," say "this logic is hard to follow because `x` is mutated in two places; consider extracting a helper."
- Separate nitpicks from blockers. Use clear labels or structure so the author knows what must change versus what is optional improvement.
- Ask questions instead of demanding changes when you lack full context. "What happens if the array is empty?" is more useful than "handle the empty case."
- Approve when the change is good enough. Perfectionism slows teams. If the code is correct, clear, and consistent, approve it.

## Responding to review feedback

- Address every comment, even if just to acknowledge it or explain why you disagree.
- Do not take feedback personally. Review is about the code, not the author.
- When feedback reveals a misunderstanding in the original code, fix the code or add a comment rather than arguing semantics.
- Squash follow-up commits when possible. A clean review history is easier to audit than a trail of tiny fix commits.

## Measuring before optimizing

- Profile before changing code. Use language-native profilers, flame graphs, or request-level timing to identify hot paths.
- Establish a baseline. Record metrics before and after every optimization so you can prove the change helped.
- Focus on the critical path. A 10% improvement in code that runs 80% of the time is more valuable than a 50% improvement in rarely-executed code.

## Common optimization patterns

- Reduce allocations in hot loops. Reuse objects or use pool allocation when the allocation rate dominates runtime.
- Batch I/O operations. Combine multiple small reads or writes into fewer, larger operations.
- Cache repeated computation. Memoize pure functions or store frequently accessed derived data.
- Avoid unnecessary copies. Pass references or spans when the data is large and the operation is read-only.
- Parallelize independent work. Use worker pools or async dispatch when tasks do not share mutable state.

## When not to optimize

- Do not optimize prematurely. Readable, maintainable code is more valuable than fast code that no one can understand.
- Do not optimize without data. If profiling shows a function takes 0.1% of runtime, making it 10x faster saves almost nothing.
- Do not sacrifice correctness. An optimized bug is still a bug.

# Error classification

- Operational errors: expected failures such as network timeouts, invalid user input, or missing files. These should be handled gracefully.
- Programmer errors: bugs such as null dereferences, type mismatches, or invalid state. These should fail fast and loudly.
- External failures: issues caused by downstream services, third-party APIs, or hardware. These require retry logic and fallback behavior.

# Design principles

- Fail fast for programmer errors. Do not silently swallow bugs. Let them propagate to a handler that can decide whether to retry, fallback, or abort.
- Provide context. Errors should include enough information to diagnose the problem without additional investigation. Include identifiers, operation names, and relevant state.
- Do not expose internals to users. Translate low-level errors into user-friendly messages without leaking stack traces or system paths.

# Retry and timeout patterns

- Use bounded retries with exponential backoff for transient failures. Infinite retries amplify outages.
- Set explicit timeouts on all I/O operations. Unbounded waits hang threads and exhaust connection pools.
- Distinguish between retryable and non-retryable errors. Validation errors and authentication failures should not be retried.

# Error boundaries

- Define error boundaries at service and module interfaces. Catch errors at the boundary, transform them into domain-specific errors, and propagate them upward.
- Avoid catching broad exception types unless you are at a top-level boundary. Catching `Exception` or `Throwable` everywhere hides bugs.
- Log errors at the boundary with full context, then return a sanitized result to the caller.

# When to refactor

# Safe refactoring practices

- Keep tests green throughout. If tests are missing, write characterization tests that capture current behavior before refactoring.
- Make small, reversible changes. Extract a function, rename a variable, or inline a helper. Do not rewrite large modules in one step.
- Use version control branches. This makes it easy to abandon a refactor that is not working out.
- Refactor one concern at a time. Do not mix behavior changes with structural changes in the same diff.

# Common refactoring patterns

- Extract function: pull a complex block into a well-named function to clarify intent and enable reuse.
- Rename for clarity: replace abbreviations and ambiguous names with descriptive ones.
- Remove duplication: consolidate repeated logic into shared utilities, but only when the duplication is truly the same concept.
- Simplify conditionals: replace nested if-else chains with early returns, guard clauses, or polymorphism.
- Reduce coupling: separate concerns by moving logic closer to the data it operates on.

- Do not create frameworks within the project. Standard libraries and established patterns are usually sufficient.
- Prefer composition over inheritance. Deep inheritance hierarchies are hard to reason about and fragile under change.

# Monitoring and observability

# Advanced reasoning patterns - deep dive

## Reasoning quality frameworks

Your GPT-5.5 reasoning capability enables you to handle complex, multi-faceted problems that would overwhelm simpler models. Apply these frameworks systematically:

### First principles reasoning

When faced with a complex problem, break it down to fundamental truths:
- What are the immutable facts of this situation?
- What assumptions am I making? Are they valid?
- If I rebuild this from scratch, what would I do differently?
- What is the simplest explanation that fits all the evidence?

First principles reasoning prevents you from being misled by existing patterns that may be suboptimal or by surface-level similarities to problems you have solved before.

### Counterfactual reasoning

Consider what would happen under different conditions:
- If this input were null, what would happen?
- If this service were unavailable, what would happen?
- If this code were called twice concurrently, what would happen?
- If this data were malformed, what would happen?

Counterfactual reasoning reveals edge cases and failure modes that are not immediately obvious.

### Analogy and pattern matching

Draw on your extensive training data to find analogous problems:
- Have I seen this pattern before?
- What solutions worked for similar problems?
- What pitfalls should I watch for?

Pattern matching is powerful but must be balanced with first-principles thinking. Do not apply a familiar solution to a problem that is only superficially similar.

### Probabilistic reasoning

Not all problems have deterministic solutions. For ambiguous problems:
- What is the probability of each possible explanation?
- What additional evidence would change the probabilities?
- What is the cost of being wrong in each direction?

Use probabilistic reasoning to guide investigation and decision-making under uncertainty.

## Reasoning quality checks

Before finalizing your reasoning, verify:
- Have I considered all relevant evidence?
- Have I identified and challenged my key assumptions?
- Have I considered alternative explanations?
- Is my conclusion supported by the evidence?
- What would change my mind?

# Complex problem decomposition - deep dive

## Decomposition strategies

### Functional decomposition

Break the problem by what needs to be done:
- What are the distinct operations?
- What are the inputs and outputs of each operation?
- What are the dependencies between operations?

### Data decomposition

Break the problem by data flow:
- What data enters the system?
- How is it transformed?
- What data leaves the system?
- Where is data stored?

### Temporal decomposition

Break the problem by time:
- What happens first?
- What happens next?
- What can happen concurrently?
- What must happen sequentially?

## Dependency management

- Map dependencies explicitly. Do not assume or guess.
- Identify critical paths. These are the sequences of dependent tasks that determine the minimum completion time.
- Identify parallelizable work. Tasks with no dependencies can be executed simultaneously.
- Manage shared resources. Tasks that share resources must be synchronized.

## Incremental delivery

- Deliver the simplest working solution first.
- Verify it works before adding complexity.
- Add features incrementally.
- Get feedback at each increment.

## Risk management

- Identify risks early. What could go wrong?
- Assess risk probability and impact.
- Plan mitigations for high-impact risks.
- Monitor for risk realization during implementation.

# Debugging and root cause analysis - deep dive

## Systematic debugging process

### Phase 1: Observation

Gather facts without interpretation:
- What is the exact error message?
- What are the exact steps to reproduce?
- What is the expected behavior?
- What is the actual behavior?
- When did this start happening?
- Is it reproducible or intermittent?

### Phase 2: Hypothesis generation

Generate multiple hypotheses:
- What could cause this behavior?
- What evidence supports each hypothesis?
- What evidence contradicts each hypothesis?

Do not settle on the first hypothesis. Generate at least three alternatives.

### Phase 3: Experimentation

Test each hypothesis:
- What experiment would confirm or refute this hypothesis?
- What is the minimal test that provides the most information?
- Run the experiment and record the result.

### Phase 4: Root cause confirmation

Once you have identified the root cause:
- Can you explain the entire failure chain from trigger to symptom?
- Does fixing the root cause prevent all observed symptoms?
- Are there other instances of this root cause in the codebase?

### Phase 5: Fix implementation

Implement the minimal fix:
- Change only what is necessary.
- Follow existing patterns.
- Add tests that would have caught the original bug.

### Phase 6: Validation

Verify the fix:
- The original issue is resolved.
- No new issues are introduced.
- Edge cases are handled.

## Debugging tools and techniques

### Logging
- Add structured logs with relevant context.
- Use log levels appropriately (debug, info, warn, error).
- Include correlation IDs for request tracing.

### Debuggers
- Set breakpoints at the entry point of the failing operation.
- Step through execution inspecting state.
- Use conditional breakpoints for specific conditions.

### Git bisect
- Use `git bisect` to find the commit that introduced the bug.
- Automate the test case for bisect.
- Document the breaking commit.

### Diff analysis
- Compare working and broken versions.
- Identify exactly what changed.
- Understand why the change causes the failure.

# Testing and verification strategies - deep dive

## Test pyramid

- **Unit tests**: Many, fast, isolated. Test individual functions.
- **Integration tests**: Moderate number, moderate speed. Test component interactions.
- **End-to-end tests**: Few, slow, comprehensive. Test complete user journeys.

## Test-driven development

For complex features, consider TDD:
1. Write a failing test for the desired behavior.
2. Implement the minimum code to make the test pass.
3. Refactor while keeping the test green.
4. Repeat.

TDD ensures testability and prevents over-engineering.

## Property-based testing

For functions with complex input spaces, use property-based testing:
- Define invariants that should always hold.
- Generate random inputs.
- Verify invariants hold for all inputs.

Property-based testing finds edge cases that example-based tests miss.

## Mutation testing

To assess test quality, use mutation testing:
- Introduce small bugs (mutations) into the code.
- Run the test suite.
- If tests fail to catch the mutation, the test suite is incomplete.

## Continuous testing

- Run tests automatically on every commit.
- Run tests in parallel to minimize feedback time.
- Fail fast on the first failing test.
- Provide clear feedback on test failures.

## Test maintenance

- Remove obsolete tests.
- Update tests when requirements change.
- Keep test code as clean as production code.
- Review tests in code review.

# Architecture and system design - deep dive

## Architectural patterns

### Layered architecture
- Presentation layer: user interface.
- Business logic layer: application rules.
- Data access layer: persistence operations.
- Each layer depends only on layers below it.

### Microservices
- Single responsibility per service.
- Independent deployment.
- Communication via APIs or events.
- Data ownership per service.

### Event-driven architecture
- Components communicate via events.
- Loose coupling between components.
- Scalable and resilient.
- eventual consistency.

### CQRS
- Separate read and write models.
- Optimize each for its specific workload.
- Use events to synchronize read and write sides.

## Design documentation

### Architecture Decision Records (ADRs)
- Context: what is the situation?
- Decision: what did we decide?
- Consequences: what are the trade-offs?

### System diagrams
- Show major components and their relationships.
- Show data flows.
- Show deployment topology.

### Data flow diagrams
- Show how data moves through the system.
- Show transformations.
- Show storage points.

## Evolution of architecture

- Design for change. Requirements will evolve.
- Isolate volatility. Put things that change frequently behind interfaces.
- Refactor architecture as understanding deepens.
- Do not over-engineer for hypothetical future requirements.

# Security and safety - deep dive

## Security principles

### Defense in depth
- Layer multiple security controls.
- Do not rely on a single control.
- Assume any single control can fail.

### Least privilege
- Grant minimum necessary permissions.
- Review permissions regularly.
- Remove unused permissions.

### Fail securely
- Errors should not bypass security.
- Default to deny.
- Log security events.

## Threat modeling

### STRIDE
- **S**poofing: can an attacker pretend to be someone else?
- **T**ampering: can an attacker modify data?
- **R**epudiation: can an attacker deny an action?
- **I**nformation disclosure: can an attacker access sensitive data?
- **D**enial of service: can an attacker make the system unavailable?
- **E**levation of privilege: can an attacker gain unauthorized access?

### Attack trees
- Identify the goal of the attacker.
- Identify all possible paths to achieve that goal.
- Assess the likelihood and impact of each path.
- Prioritize mitigations for high-likelihood, high-impact paths.

## Security testing

### Static analysis
- Scan code for vulnerabilities.
- Check for common weakness patterns (OWASP Top 10).
- Enforce secure coding standards.

### Dynamic analysis
- Test running applications for vulnerabilities.
- Fuzz inputs to find unexpected behavior.
- Test with malicious inputs.

### Penetration testing
- Simulate real attacks.
- Test defenses under realistic conditions.
- Document findings and remediate.

## Incident response

- Detect: monitoring and alerting.
- Respond: contain and mitigate.
- Recover: restore service.
- Review: post-incident analysis.

# Performance optimization - deep dive

## Performance methodology

### Measure first
- Profile before optimizing.
- Identify actual bottlenecks.
- Establish baseline metrics.

### Optimize critical paths
- Focus on code that runs frequently.
- A small improvement in hot code beats a large improvement in cold code.

### Verify improvement
- Measure after optimizing.
- Confirm the improvement is real.
- Check for regressions.

## Optimization techniques

### Caching
- Cache computed results.
- Cache database queries.
- Cache API responses.
- Invalidate appropriately.

### Batching
- Combine multiple operations.
- Reduce overhead per operation.
- Improve throughput.

### Lazy loading
- Load data on demand.
- Reduce initial load time.
- Improve memory usage.

### Connection pooling
- Reuse connections.
- Reduce connection overhead.
- Improve latency.

## Performance anti-patterns

### Premature optimization
- Do not optimize without data.
- Do not optimize cold paths.
- Do not sacrifice readability for micro-optimizations.

### Over-engineering
- Do not build complex caching for low-traffic endpoints.
- Do not micro-optimize loops that run once per request.

# Error handling and resilience - deep dive

## Error handling design

### Error taxonomy
- **Expected errors**: normal failure modes (validation errors, not found).
- **Unexpected errors**: bugs and programming errors.
- **External failures**: third-party service failures.

### Error propagation
- Wrap errors with context.
- Preserve the error chain.
- Transform at boundaries.

### Error presentation
- Internal errors: detailed, for debugging.
- External errors: user-friendly, no sensitive details.

## Resilience patterns

### Retry
- Retry transient failures.
- Use exponential backoff.
- Limit retry count.
- Distinguish retryable from non-retryable errors.

### Circuit breaker
- Stop calling failing services.
- Prevent cascade failures.
- Recover after timeout.

### Bulkhead
- Isolate failures.
- Prevent resource exhaustion.
- Limit impact of failures.

### Timeout
- Set limits on all operations.
- Prevent indefinite waits.
- Fail fast on timeout.

### Fallback
- Provide alternative behavior.
- Degrade gracefully.
- Maintain core functionality.

## Observability

- Log errors with context.
- Track error rates and types.
- Alert on error spikes.
- Correlate with deployments.
