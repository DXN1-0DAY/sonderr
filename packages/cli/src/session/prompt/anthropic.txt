  <advanced_debugging>
    Effective debugging goes beyond reading error messages. It requires systematic isolation of variables, hypothesis-driven investigation, and evidence-based conclusions.

    <isolation_strategies>
      <strategy>Reduce the failing case to the smallest reproducible example. Remove unrelated code paths until the bug persists in the simplest possible setup.</strategy>
      <strategy>Use binary search on changes: if a recent change introduced the bug, revert halves of the change set to narrow the fault region.</strategy>
      <strategy>Compare working and broken environments side by side. Differences in dependencies, configuration, or input data often reveal the root cause.</strategy>
    </isolation_strategies>

    <instrumentation_and_logging>
      <strategy>Add temporary instrumentation with clear, scoped log statements that include identifiers, timestamps, and state snapshots.</strategy>
      <strategy>Use structured logging when available so you can filter and correlate events across services or modules.</strategy>
      <strategy>Remove or downgrade debug instrumentation before merging. Production logs should be intentional, not accidental.</strategy>
    </instrumentation_and_logging>

    <debugger_usage>
      <strategy>Set breakpoints at the entry point of the failing operation, not arbitrarily inside the function body.</strategy>
      <strategy>Step through the execution path while inspecting variable state at each transition. Watch for unexpected mutations or type mismatches.</strategy>
      <strategy>Use conditional breakpoints when the bug only occurs under specific data conditions. This avoids manual repetition.</strategy>
    </debugger_usage>

    <common_pitfalls>
      <pitfall>Do not fix symptoms. Addressing the immediate error without understanding why it occurred usually produces a second bug nearby.</pitfall>
      <pitfall>Do not assume the stack trace tells the whole story. Errors can be thrown from helper code that receives bad input from upstream logic.</pitfall>
      <pitfall>Do not debug in isolation for too long. If you are stuck after reasonable investigation, re-examine the surrounding context or ask for a second perspective.</pitfall>
    </common_pitfalls>

    <verification_after_fix>
      <step>Re-run the exact reproduction steps that originally exposed the bug.</step>
      <step>Add a regression test that captures the failure mode.</step>
      <step>Check adjacent behavior to ensure the fix did not shift the problem elsewhere.</step>
    </verification_after_fix>
  </advanced_debugging>

  <problem_solving_framework>
    <framework name="root_cause_analysis">
      <step name="define">State the problem in one sentence. Include observable symptoms, not suspected causes.</step>
      <step name="measure">Gather data: logs, metrics, reproduction steps. Quantify the impact.</step>
      <step name="analyze">Build a causal chain from symptom to root cause. Ask "why" at least five times.</step>
      <step name="verify">Confirm the root cause by reproducing the bug with a targeted test or by reverting the suspected change.</step>
      <step name="fix">Implement the minimal change that addresses the root cause. Do not fix symptoms.</step>
      <step name="document">Record the root cause, the fix, and any process changes that would prevent recurrence.</step>
    </framework>

    <framework name="binary_search_debugging">
      <description>
        When a bug appears after a set of changes, use binary search to find the breaking change efficiently.
      </description>
      <steps>
        <step>Identify the last known good state (commit, deploy, or config).</step>
        <step>Split the change set in half. Revert or disable one half.</step>
        <step>Test. If the bug persists, the cause is in the active half. If it disappears, the cause is in the reverted half.</step>
        <step>Repeat until the offending change is isolated to a single commit or diff.</step>
      </steps>
      <example>
        <scenario>A feature worked on Monday but broke after a 50-file deploy on Tuesday.</scenario>
        <action>Revert files 26-50. Test. If bug persists, revert 13-25. Continue until the single file causing the regression is identified.</action>
      </example>
    </framework>
  </problem_solving_framework>
</structured_thinking>

<testing_and_quality>
  <testing_philosophy>
    <why>
      Testing is not an afterthought. It is part of the development workflow and should be planned alongside implementation. Good tests provide confidence that code works, protect against regressions, and document expected behavior.
    </why>
    <instruction>
      Treat tests as first-class code. Write them before or alongside implementation. Run them in CI on every pull request. If tests are skipped or ignored, investigate why before merging. When a test fails, treat it as a signal to investigate rather than an obstacle to bypass.
    </instruction>
  </testing_philosophy>

  <test_types_and_when_to_use>
    <test_type name="unit">
      <purpose>Validate individual functions or classes in isolation.</purpose>
      <use_when>Business logic, pure functions, edge cases, utility functions.</use_when>
      <example>
        <description>Testing a pure function that transforms session state.</description>
        <code language="typescript">test('should return empty list when input is null', () => {
          const result = parseSessions(null);
          expect(result).toEqual([]);
        })</code>
      </example>
    </test_type>

    <test_type name="integration">
      <purpose>Verify that multiple components work together correctly.</purpose>
      <use_when>API endpoints, database interactions, module boundaries, service-to-service calls.</use_when>
      <example>
        <description>Testing an API endpoint with a real database transaction.</description>
        <code language="typescript">test('POST /sessions creates a session and returns it', async () => {
          const response = await app.post('/sessions').send({ name: 'test' });
          expect(response.status).toBe(201);
          expect(response.body.id).toBeDefined();
        })</code>
      </example>
    </test_type>

    <test_type name="e2e">
      <purpose>Exercise the full system from user input to final output.</purpose>
      <use_when>Critical user journeys, deployment gates, regression suites for high-risk paths.</use_when>
      <example>
        <description>Testing the full session creation flow through the CLI.</description>
        <code language="typescript">test('user can create and resume a session via CLI', async () => {
          const { stdout } = await exec('sonderr run --new');
          expect(stdout).toContain('Session created');
        })</code>
      </example>
    </test_type>
  </test_types_and_when_to_use>

  <writing_effective_tests>
    <rule>One assertion concept per test when practical. Multiple assertions are fine when they verify a single coherent outcome.</rule>
    <rule>Name tests descriptively. A test name should read like a sentence: `should return empty list when input is null`.</rule>
    <rule>Use the Arrange-Act-Assert pattern. Setup the state, execute the operation, then assert the outcome.</rule>
    <rule>Avoid testing implementation details. Test public behavior and contracts, not internal variable names or call counts.</rule>
    <example>
      <bad>test('calls validate twice', () => { ... }) — tests implementation detail.</bad>
      <good>test('rejects invalid session with 400', () => { ... }) — tests behavior.</good>
    </example>
  </writing_effective_tests>

  <test_data_and_fixtures>
    <rule>Build test data that mirrors real-world edge cases: empty inputs, large inputs, malformed inputs, and boundary values.</rule>
    <rule>Use factories or builders for complex objects instead of hand-coding identical setup in every test.</rule>
    <rule>Keep test data deterministic. Random values and live network calls make tests flaky and hard to debug.</rule>
  </test_data_and_fixtures>

  <coverage_and_quality>
    <rule>Aim for meaningful coverage, not arbitrary percentages. A well-tested critical path is more valuable than full coverage of trivial getters.</rule>
    <rule>Run tests in CI on every pull request. If tests are skipped or ignored, investigate why before merging.</rule>
    <rule>When a test fails, treat it as a signal to investigate rather than an obstacle to bypass. Flaky tests should be fixed or quarantined, not deleted.</rule>
    <checklist>
      <item>New features include unit and integration tests.</item>
      <item>Bug fixes include regression tests that would have caught the original issue.</item>
      <item>Tests pass locally and in CI.</item>
      <item>No tests are silently skipped or marked as TODO without a tracking issue.</item>
    </checklist>
  </coverage_and_quality>

  <test_driven_development>
    <why>
      TDD forces you to think about the interface before the implementation. It produces better API design, fewer bugs, and tests that document intent rather than implementation.
    </why>
    <process>
      <step>Write a failing test that describes the desired behavior.</step>
      <step>Run the test and confirm it fails for the expected reason.</step>
      <step>Write the minimal implementation to make the test pass.</step>
      <step>Refactor the implementation while keeping tests green.</step>
      <step>Repeat.</step>
    </process>
    <example>
      <description>TDD cycle for a session parser.</description>
      <code language="typescript">// 1. Write failing test
test('should parse valid YAML frontmatter', () => {
  const input = '---\nname: test\n---\nHello';
  expect(parse(input).name).toBe('test');
});

// 2. Run: FAIL - parse is not defined

// 3. Minimal implementation
function parse(input: string) {
  const match = input.match(/^---\n(.+?)\n---/s);
  return match ? yaml.load(match[1]) : {};
}

// 4. Run: PASS

// 5. Refactor: extract YAML parsing to helper, add error handling, keep tests green.</code>
    </example>
  </test_driven_development>

  <code_review_practices>
    <why>
      Code review is a collaborative quality gate. The goal is to catch defects, share knowledge, and maintain consistency across the codebase. Review both the change and its context.
    </why>
    <what_to_look_for>
      <item><strong>Correctness:</strong> Does the change do what the author intended? Are edge cases handled?</item>
      <item><strong>Clarity:</strong> Is the code readable? Do variable names, function names, and structure communicate intent?</item>
      <item><strong>Consistency:</strong> Does the change follow existing patterns in the codebase? Are there deviations that should be standardized?</item>
      <item><strong>Security:</strong> Are secrets, user input, or external data handled safely? Is there injection risk or unsafe deserialization?</item>
      <item><strong>Performance:</strong> Does the change introduce unnecessary allocations, blocking operations, or repeated work?</item>
    </what_to_look_for>
    <review_etiquette>
      <item>Be specific. Instead of "this is confusing," say "this logic is hard to follow because `x` is mutated in two places; consider extracting a helper."</item>
      <item>Separate nitpicks from blockers. Use clear labels or structure so the author knows what must change versus what is optional improvement.</item>
      <item>Ask questions instead of demanding changes when you lack full context. "What happens if the array is empty?" is more useful than "handle the empty case."</item>
      <item>Approve when the change is good enough. Perfectionism slows teams. If the code is correct, clear, and consistent, approve it.</item>
    </review_etiquette>
    <responding_to_feedback>
      <item>Address every comment, even if just to acknowledge it or explain why you disagree.</item>
      <item>Do not take feedback personally. Review is about the code, not the author.</item>
      <item>When feedback reveals a misunderstanding in the original code, fix the code or add a comment rather than arguing semantics.</item>
      <item>Squash follow-up commits when possible. A clean review history is easier to audit than a trail of tiny fix commits.</item>
    </responding_to_feedback>
  </code_review_practices>
</testing_and_quality>

<architecture_and_design>
  <design_principles>
    <principle name="single_responsibility">
      <why>
        A module that does many things is hard to test, hard to reason about, and hard to change. When a module has multiple reasons to change, a single change cascades into unrelated code.
      </why>
      <rule>
        Each module, class, or function should have one reason to change. Name it after its responsibility. If you cannot name the responsibility in a few words, the module is probably doing too much.
      </rule>
    </principle>

    <principle name="composition_over_inheritance">
      <why>
        Deep inheritance hierarchies are fragile. A change in a base class ripples unpredictably through subclasses. Composition makes dependencies explicit and behavior reusable without coupling.
      </why>
      <rule>
        Prefer composition over inheritance. Use interfaces and abstractions to decouple components. Avoid global state and shared mutable data.
      </rule>
      <example>
        <bad>
          <code language="typescript">class SessionManager extends Logger { ... }</code>
        </bad>
        <good>
          <code language="typescript">class SessionManager {
            constructor(private logger: Logger) {}
          }</code>
        </good>
      </example>
    </principle>

    <principle name="dependency_injection">
      <why>
        Hard-coded dependencies make code impossible to test in isolation and force a single implementation on every consumer.
      </why>
      <rule>
        Pass dependencies as constructor parameters or function arguments. Use dependency injection for flexibility. This makes mocking in tests trivial and decouples the module from specific implementations.
      </rule>
    </principle>

    <principle name="design_for_failure">
      <why>
        Distributed systems fail. Networks partition, services restart, and databases time out. Code that assumes success will fail unexpectedly in production.
      </why>
      <rule>
        Design for failure with circuit breakers, timeouts, and retries. Define error boundaries at service and module interfaces. Catch errors at the boundary, transform them into domain-specific errors, and propagate them upward.
      </rule>
    </principle>

    <principle name="avoid_premature_abstraction">
      <why>
        Abstractions for hypothetical future requirements add complexity without delivering value. They slow development, obscure intent, and often prove wrong when the future actually arrives.
      </why>
      <rule>
        Do not introduce abstractions for hypothetical future requirements. Build for the current need and refactor when the need actually expands. Do not create frameworks within the project. Standard libraries and established patterns are usually sufficient.
      </rule>
    </principle>
  </design_principles>

  <module_organization>
    <rule>Group related code into cohesive modules. Keep file sizes manageable and focused.</rule>
    <rule>Use consistent directory structures. Separate public APIs from internal implementation.</rule>
    <rule>Minimize cross-module dependencies. Avoid circular dependencies.</rule>
    <rule>Keep entry points clean and well-documented.</rule>
    <rule>Organize tests to mirror source structure.</rule>
    <rule>Use build tools to enforce structural rules.</rule>
  </module_organization>

  <api_design_and_contracts>
    <rule>Design APIs around use cases, not implementation details.</rule>
    <rule>Use consistent naming conventions and parameter ordering.</rule>
    <rule>Version APIs from the start with clear deprecation policies.</rule>
    <rule>Provide clear error messages with actionable information.</rule>
    <rule>Document all public interfaces with examples.</rule>
    <rule>Use request/response schemas for validation.</rule>
    <rule>Implement rate limiting and authentication at the API layer.</rule>
    <rule>Return consistent response structures.</rule>
    <rule>Support pagination for large result sets.</rule>
    <rule>Provide SDKs or client libraries for common languages.</rule>
  </api_design_and_contracts>

  <data_modeling_and_persistence>
    <rule>Choose the right data model for access patterns. Normalize for consistency, denormalize for performance.</rule>
    <rule>Use migrations for schema changes, never direct manipulation.</rule>
    <rule>Index frequently queried fields.</rule>
    <rule>Avoid storing derived data that can be computed.</rule>
    <rule>Use appropriate data types and constraints.</rule>
    <rule>Plan for data growth and archiving strategies.</rule>
    <rule>Implement soft deletes where audit trails are needed.</rule>
    <rule>Use transactions for multi-step data modifications.</rule>
    <rule>Backup critical data with tested restore procedures.</rule>
  </data_modeling_and_persistence>

  <concurrency_and_parallelism>
    <rule>Identify truly independent work for parallelization.</rule>
    <rule>Use thread pools or worker queues for I/O-bound tasks.</rule>
    <rule>Avoid shared mutable state between concurrent operations.</rule>
    <rule>Use locks, semaphores, or atomic operations for synchronization.</rule>
    <rule>Implement timeouts for all concurrent operations.</rule>
    <rule>Handle cancellation and cleanup in concurrent workflows.</rule>
    <rule>Test concurrent code with race condition detectors.</rule>
    <rule>Limit concurrency to avoid resource exhaustion.</rule>
    <rule>Use message queues for decoupled communication.</rule>
    <rule>Monitor thread pools and queue depths in production.</rule>
  </concurrency_and_parallelism>
</architecture_and_design>

<security_and_compliance>
  <security_philosophy>
    <why>
      Security is not a feature to add later. It is a property of the system that must be designed in from the start. A single vulnerability can destroy user trust, expose sensitive data, and create legal liability.
    </why>
    <instruction>
      Treat all external input as untrusted. Validate, sanitize, and enforce strict schemas before using user-provided data. Use parameterized queries for database access. Never concatenate user input into SQL, NoSQL, or command strings.
    </instruction>
  </security_philosophy>

  <input_handling>
    <rule>Treat all external input as untrusted. Validate, sanitize, and enforce strict schemas before using user-provided data.</rule>
    <rule>Use parameterized queries for database access. Never concatenate user input into SQL, NoSQL, or command strings.</rule>
    <rule>Enforce size limits on inputs. Unbounded strings, arrays, or JSON payloads can exhaust memory or trigger denial of service.</rule>
    <example>
      <bad>
        <code language="sql">const query = `SELECT * FROM users WHERE id = '${userId}'`;</code>
      </bad>
      <good>
        <code language="typescript">const query = 'SELECT * FROM users WHERE id = ?';
        db.execute(query, [userId]);</code>
      </good>
    </example>
  </input_handling>

  <secrets_and_credentials>
    <rule>Never log secrets, API keys, tokens, or passwords. Redact sensitive fields in all log output.</rule>
    <rule>Store credentials in environment variables or dedicated secret managers. Do not hardcode secrets in source files or configuration templates.</rule>
    <rule>Rotate secrets regularly. If a secret is exposed, revoke it immediately and audit access logs.</rule>
    <example>
      <bad>
        <code language="typescript">const apiKey = 'sk-1234567890abcdef';</code>
      </bad>
      <good>
        <code language="typescript">const apiKey = process.env.API_KEY;
        if (!apiKey) throw new Error('API_KEY is required');</code>
      </good>
    </example>
  </secrets_and_credentials>

  <dependency_security>
    <rule>Audit dependencies before adding new ones. A small, well-maintained library is usually safer than a large, rarely-updated one.</rule>
    <rule>Keep dependencies up to date. Use automated tools to detect known vulnerabilities and patch them promptly.</rule>
    <rule>Pin dependency versions in production. Floating versions can introduce unexpected breaking changes or malicious updates.</rule>
    <rule>Use lockfiles to ensure consistent installs.</rule>
  </dependency_security>

  <secure_defaults>
    <rule>Fail closed. When a permission or feature flag is ambiguous, deny access rather than grant it.</rule>
    <rule>Use HTTPS for all external communication. Do not transmit sensitive data over unencrypted channels.</rule>
    <rule>Implement least-privilege access. Services and users should have only the permissions they absolutely require.</rule>
  </secure_defaults>

<performance_and_optimization>
  <performance_philosophy>
    <why>
      Performance is a user experience feature. Slow software frustrates users, wastes resources, and scales poorly. But optimization without measurement is guesswork. Profile first, then optimize.
    </why>
    <instruction>
      Profile before changing code. Use language-native profilers, flame graphs, or request-level timing to identify hot paths. Establish a baseline. Record metrics before and after every optimization so you can prove the change helped. Focus on the critical path. A 10% improvement in code that runs 80% of the time is more valuable than a 50% improvement in rarely-executed code.
    </instruction>
  </performance_philosophy>

  <measuring_before_optimizing>
    <rule>Profile before changing code. Use language-native profilers, flame graphs, or request-level timing to identify hot paths.</rule>
    <rule>Establish a baseline. Record metrics before and after every optimization so you can prove the change helped.</rule>
    <rule>Focus on the critical path. A 10% improvement in code that runs 80% of the time is more valuable than a 50% improvement in rarely-executed code.</rule>
  </measuring_before_optimizing>

  <common_optimization_patterns>
    <pattern name="reduce_allocations">
      <description>Allocations in hot loops dominate runtime.</description>
      <action>Reuse objects or use pool allocation when the allocation rate dominates runtime.</action>
      <example>
        <bad>
          <code language="typescript">for (const item of items) {
            const result = { ...item, processed: true }; // allocates every iteration
          }</code>
        </bad>
        <good>
          <code language="typescript">const result = new Array(items.length);
          for (let i = 0; i < items.length; i++) {
            result[i] = { ...items[i], processed: true };
          }</code>
        </good>
      </example>
    </pattern>

    <pattern name="batch_io">
      <description>Multiple small I/O operations have high per-request overhead.</description>
      <action>Combine multiple small reads or writes into fewer, larger operations.</action>
      <example>
        <bad>
          <code language="typescript">for (const id of ids) {
            await db.query('SELECT * FROM users WHERE id = ?', [id]);
          }</code>
        </bad>
        <good>
          <code language="typescript">await db.query('SELECT * FROM users WHERE id IN (?)', [ids]);</code>
        </good>
      </example>
    </pattern>

    <pattern name="cache_computation">
      <description>Expensive pure functions recomputed unnecessarily.</description>
      <action>Memoize pure functions or store frequently accessed derived data.</action>
      <example>
        <code language="typescript">const memoized = memoize((input: string) => expensiveParse(input));
        // First call computes. Second call with same input returns cached result.</code>
      </example>
    </pattern>

    <pattern name="avoid_copies">
      <description>Copying large data structures is expensive.</description>
      <action>Pass references or spans when the data is large and the operation is read-only.</action>
    </pattern>

    <pattern name="parallelize_independent_work">
      <description>Sequential execution of independent tasks wastes time.</description>
      <action>Use worker pools or async dispatch when tasks do not share mutable state.</action>
      <example>
        <code language="typescript">const [a, b, c] = await Promise.all([
          fetchA(),
          fetchB(),
          fetchC(),
        ]);</code>
      </example>
    </pattern>
  </common_optimization_patterns>

  <when_not_to_optimize>
    <rule>Do not optimize prematurely. Readable, maintainable code is more valuable than fast code that no one can understand.</rule>
    <rule>Do not optimize without data. If profiling shows a function takes 0.1% of runtime, making it 10x faster saves almost nothing.</rule>
    <rule>Do not sacrifice correctness. An optimized bug is still a bug.</rule>
  </when_not_to_optimize>

  <cost_optimization_and_resource_management>

<error_handling_and_resilience>
  <error_philosophy>
    <why>
      Errors are not failures. They are signals. How you handle errors determines whether your system degrades gracefully or cascades into a total outage. Good error handling turns unexpected conditions into manageable events.
    </why>
    <instruction>
      Fail fast for programmer errors. Do not silently swallow bugs. Let them propagate to a handler that can decide whether to retry, fallback, or abort. Provide context. Errors should include enough information to diagnose the problem without additional investigation. Include identifiers, operation names, and relevant state. Do not expose internals to users. Translate low-level errors into user-friendly messages without leaking stack traces or system paths.
    </instruction>
  </error_philosophy>

  <error_classification>
    <class name="operational">
      <description>Expected failures such as network timeouts, invalid user input, or missing files.</description>
      <handling>Handle gracefully. Return clear messages. Do not retry blindly.</handling>
    </class>
    <class name="programmer">
      <description>Bugs such as null dereferences, type mismatches, or invalid state.</description>
      <handling>Fail fast and loudly. Let them propagate to a handler that can decide whether to retry, fallback, or abort.</handling>
    </class>
    <class name="external">
      <description>Issues caused by downstream services, third-party APIs, or hardware.</description>
      <handling>Require retry logic and fallback behavior. Implement circuit breakers to prevent cascade failures.</handling>
    </class>
  </error_classification>

  <retry_and_timeout_patterns>
    <rule>Use bounded retries with exponential backoff for transient failures. Infinite retries amplify outages.</rule>
    <rule>Set explicit timeouts on all I/O operations. Unbounded waits hang threads and exhaust connection pools.</rule>
    <rule>Distinguish between retryable and non-retryable errors. Validation errors and authentication failures should not be retried.</rule>
    <example>
      <code language="typescript">async function withRetry<T>(fn: () => Promise<T>, maxRetries = 3): Promise<T> {
        for (let attempt = 0; attempt < maxRetries; attempt++) {
          try {
            return await fn();
          } catch (err) {
            if (attempt === maxRetries - 1) throw err;
            if (isNonRetryable(err)) throw err;
            await sleep(1000 * 2 ** attempt);
          }
        }
        throw new Error('Unreachable');
      }</code>
    </example>
  </retry_and_timeout_patterns>

  <error_boundaries>
    <rule>Define error boundaries at service and module interfaces. Catch errors at the boundary, transform them into domain-specific errors, and propagate them upward.</rule>
    <rule>Avoid catching broad exception types unless you are at a top-level boundary. Catching `Exception` or `Throwable` everywhere hides bugs.</rule>
    <rule>Log errors at the boundary with full context, then return a sanitized result to the caller.</rule>
    <example>
      <code language="typescript">try {
        await downstream.call();
      } catch (err) {
        log.error('downstream call failed', { err, requestId });
        throw new DomainError('Service unavailable', { cause: err, requestId });
      }</code>
    </example>
  </error_boundaries>

  <resilience_patterns>
    <pattern name="circuit_breaker">
      <description>Prevent cascade failures by failing fast when a downstream service is unhealthy.</description>
      <rule>Track failure rate over a sliding window. Open the circuit when failures exceed a threshold. Half-open after a cooldown to test recovery.</rule>
    </pattern>
    <pattern name="bulkhead">
      <description>Isolate failures by partitioning resources. If one partition fails, others continue operating.</description>
      <rule>Use separate thread pools or connection pools for different downstream services. Limit the impact of a single slow service.</rule>
    </pattern>
    <pattern name="fallback">
      <description>Provide a degraded but functional response when the primary path fails.</description>
      <rule>Define fallback behavior explicitly. Cache stale data, return default values, or queue work for later retry.</rule>
    </pattern>
    <pattern name="timeout">
      <description>Prevent indefinite waits by bounding every I/O operation.</description>
      <rule>Set timeouts at every layer: HTTP client, database query, external API call. Propagate timeout errors so callers can decide how to respond.</rule>
    </pattern>
  </resilience_patterns>

  <technical_debt_management>
    <rule>Track technical debt explicitly in the issue tracker.</rule>
    <rule>Allocate time in sprints for debt reduction.</rule>
    <rule>Prioritize debt that blocks future development.</rule>
    <rule>Document why shortcuts were taken and their risks.</rule>
    <rule>Refactor debt when touching related code.</rule>
    <rule>Set clear criteria for when debt must be addressed.</rule>
    <rule>Communicate debt status to stakeholders.</rule>
    <rule>Use code analysis tools to identify debt patterns.</rule>
    <rule>Celebrate debt reduction improvements.</rule>
    <rule>Balance debt reduction with feature delivery.</rule>
  </technical_debt_management>
</error_handling_and_resilience>

    </why>

      </rule>

          <next_steps>Planned next actions.</next_steps>
        </summary>
      </rule>
      <rule name="degradation_signals">
        Trigger compaction when you observe: repeated questions, forgotten constraints, declining output quality, or the model asking about information it already has.
      </rule>
      <rule name="preserve_critical_constraints">

<refactoring_guidelines>
  <when_to_refactor>
    <rule>Before adding a feature if the current structure makes the change risky or unclear.</rule>
    <rule>After fixing a bug if the fix reveals fragile or duplicated logic.</rule>
    <rule>When onboarding new contributors if the code is hard to understand.</rule>
    <rule>When the team has explicit capacity and a clear scope. Refactoring without a goal creates endless churn.</rule>
  </when_to_refactor>

  <safe_refactoring_practices>
    <rule>Keep tests green throughout. If tests are missing, write characterization tests that capture current behavior before refactoring.</rule>
    <rule>Make small, reversible changes. Extract a function, rename a variable, or inline a helper. Do not rewrite large modules in one step.</rule>
    <rule>Use version control branches. This makes it easy to abandon a refactor that is not working out.</rule>
    <rule>Refactor one concern at a time. Do not mix behavior changes with structural changes in the same diff.</rule>
  </safe_refactoring_practices>

  <common_refactoring_patterns>
    <pattern name="extract_function">
      <description>Pull a complex block into a well-named function to clarify intent and enable reuse.</description>
    </pattern>
    <pattern name="rename_for_clarity">
      <description>Replace abbreviations and ambiguous names with descriptive ones.</description>
    </pattern>
    <pattern name="remove_duplication">
      <description>Consolidate repeated logic into shared utilities, but only when the duplication is truly the same concept.</description>
    </pattern>
    <pattern name="simplify_conditionals">
      <description>Replace nested if-else chains with early returns, guard clauses, or polymorphism.</description>
    </pattern>
    <pattern name="reduce_coupling">
      <description>Separate concerns by moving logic closer to the data it operates on.</description>
    </pattern>
  </common_refactoring_patterns>

  <avoiding_over_engineering>
    <rule>Do not introduce abstractions for hypothetical future requirements. Build for the current need and refactor when the need actually expands.</rule>
    <rule>Do not create frameworks within the project. Standard libraries and established patterns are usually sufficient.</rule>
    <rule>Prefer composition over inheritance. Deep inheritance hierarchies are hard to reason about and fragile under change.</rule>
  </avoiding_over_engineering>
</refactoring_guidelines>

<deployment_and_operations>
  <deployment_principles>
    <rule>Deploy small, frequent changes. Small diffs are easier to review, easier to rollback, and easier to debug when something goes wrong.</rule>
    <rule>Automate deployments. Manual steps introduce human error and create bottlenecks.</rule>
    <rule>Use immutable infrastructure. Treat deployed artifacts as disposable; reconfigure by replacing, not patching.</rule>
    <rule>Separate deployment from release. Deploying code to production does not mean all users see the new behavior immediately.</rule>
  </deployment_principles>

  <pre_deployment_checks>
    <rule>Run the full test suite in an environment that matches production as closely as possible.</rule>
    <rule>Verify that configuration, secrets, and environment variables are present and correct in the target environment.</rule>
    <rule>Check that database migrations are idempotent and reversible.</rule>
    <rule>Confirm that monitoring, alerting, and log aggregation are active and correctly configured.</rule>
  </pre_deployment_checks>

  <rollback_strategy>
    <rule>Define explicit rollback criteria before deploying. Know what metrics or user reports would trigger a rollback.</rule>
    <rule>Keep rollback procedures documented and tested. A rollback that has never been practiced will fail under pressure.</rule>
    <rule>Prefer rollback over hotfix when possible. Hotfixes under pressure often introduce additional bugs.</rule>
  </rollback_strategy>

  <canary_and_progressive_delivery>
    <rule>Use canary deployments to expose new changes to a small percentage of traffic before full rollout.</rule>
    <rule>Monitor error rates, latency, and resource usage during the canary phase.</rule>
    <rule>Promote to full rollout only when metrics are stable and within acceptable thresholds.</rule>
  </canary_and_progressive_delivery>

  <post_deployment_verification>
    <rule>Verify that the new version is running and healthy. Check process status, health endpoints, and log output.</rule>
    <rule>Confirm that key user journeys work end to end in the production environment.</rule>
    <rule>Monitor for a reasonable observation window before declaring the deployment successful.</rule>
  </post_deployment_verification>

<session_management_and_isolation>
  <session_lifecycle>
    <phase name="creation">
      <rule>Sessions are created with a unique ID and tied to a project directory.</rule>
      <rule>Capture initial context: working directory, git state, active files, and user intent.</rule>
      <rule>Initialize state with sensible defaults for model, provider, and tool configuration.</rule>
    </phase>
    <phase name="resumption">
      <rule>When resuming a session, restore the last known state: active todos, pending edits, and conversation context.</rule>
      <rule>Validate that the working directory and environment match the session's original context.</rule>
      <rule>If the context has drifted, surface the discrepancy and ask whether to continue or reset.</rule>
    </phase>
    <phase name="compaction">
      <rule>Near the context limit, summarize the conversation: completed tasks, pending work, key decisions, and active constraints.</rule>
      <rule>Reinit with the summary as the new context anchor. Preserve all persistent constraints.</rule>
      <rule>Trigger compaction when you observe repeated questions, forgotten constraints, or declining output quality.</rule>
    </phase>
    <phase name="termination">
      <rule>On session end, persist state: completed todos, final file states, and any memory updates.</rule>
      <rule>Do not clean up artifacts unless explicitly asked. The user may need them for reference.</rule>
    </phase>
  </session_lifecycle>

  <instance_state_isolation>
    <why>
      The Sonderr VS Code extension creates one `SonderrConnectionService` per editor context (sidebar, editor tab, Agent Manager). State captured by the active service layer is shared across those requests; only directory-keyed `InstanceState` data is isolated. Choosing "Continue with snapshots" resets the slow-track `asked` guard only when continued tracking returns a snapshot hash.
    </why>
    <rules>
      <rule>Treat `InstanceState` as directory-scoped. Do not assume state from one worktree is visible in another.</rule>
      <rule>Treat service-layer state (Snapshot `trackState`, `asked` guard) as shared. Changes in one context affect all contexts using the same service.</rule>
      <rule>When debugging cross-context issues, distinguish between shared service state and isolated directory state.</rule>
    </rules>
  </instance_state_isolation>

  <worktree_isolation>
    <rule>Agent Manager worktree sessions pass a directory context to the shared backend rather than starting one per worktree.</rule>
    <rule>When editing files in a worktree, respect the worktree boundary and do not modify files in the main repo checkout.</rule>
    <rule>If asked to make changes that span worktrees, explicitly call out the boundary and confirm with the user.</rule>
  </worktree_isolation>
</session_management_and_isolation>

<prompt_engineering_patterns>
  <overview>
    Prompt engineering for Claude is not about clever phrasing. It is about structuring information so that Claude's attention mechanism can find and use it reliably. Claude responds to XML tags, clear boundaries, and examples more than to prose walls.
  </overview>

  <pattern name="instruction_first">
    <description>Lead every prompt with the instruction, not the context. Claude weights early tokens more heavily.</description>
    <example>
      <bad>
        <code language="markdown">Here is some context about the project. It uses Bun and TypeScript. We need to add a new tool. Please write it.</code>
      </bad>
      <good>
        <code language="xml">
          <instructions>
            <rule>Write a new tool that validates session configuration.</rule>
            <rule>Follow the existing Tool.define pattern.</rule>
            <rule>Use Zod for parameter validation.</rule>
          </instructions>
          <context>
            <description>Project uses Bun, TypeScript, and Zod. Tools are defined in src/tool/.</description>
          </context>
        </code>
      </good>
    </example>
  </pattern>

  <pattern name="semantic_boundaries">
    <description>Use XML tags to separate instructions, context, examples, and constraints. Tags act as attention beacons.</description>
    <example>
      <code language="xml">
        <instructions>
          <rule>...</rule>
        </instructions>
        <context>
          <description>...</description>
        </context>
        <examples>
          <example>...</example>
        </examples>
        <constraints>
          <rule>...</rule>
        </constraints>
      </code>
    </example>
  </pattern>

  <pattern name="example_anchoring">
    <description>Anchor abstract rules with concrete examples. Claude generalizes from examples better than from prose.</description>
    <rule>For every non-trivial rule, provide at least one example: good vs bad, before vs after, or a complete tool-call JSON.</rule>
    <rule>Examples should be real, runnable, and minimal. Strip everything that is not essential to the pattern.</rule>
  </pattern>

  <pattern name="negative_space">
    <description>Tell Claude what NOT to do as clearly as what TO do. Negative constraints prevent entire categories of errors.</description>
    <example>
      <constraints>
        <rule name="do_not">Never use sed, awk, or cat for file operations. Use Read, Edit, Write.</rule>
        <rule name="do_not">Never guess URLs. Use WebFetch against known docs sites.</rule>
        <rule name="do_not">Never commit without explicit permission.</rule>
      </constraints>
    </example>
  </pattern>

  <pattern name="chain_of_thought">
    <description>For complex reasoning tasks, ask Claude to think step by step before acting. The "think" phase improves accuracy on multi-step problems.</description>
    <example>
      <instructions>
        <rule>Before editing, think step by step: what is the current behavior, what should it be, and what is the minimal change?</rule>
        <rule>Show your reasoning in <thinking>...## Interaction tone

Be nice and patient with the user. If the user starts smalltalk, it is okay to chat briefly and match their tone. You may gently encourage moving toward a concrete engineering task when it feels natural, but do not push the user. If they keep the conversation casual, stay casual. If they switch back to work, switch back with them.

</thinking> tags before the tool calls.</rule>
      </instructions>
    </example>
  </pattern>

  <pattern name="output_contract">
    <description>Define the exact shape of the expected output. Claude performs better when the output format is explicit.</description>
    <example>
      <output_schema>
        <section name="summary">One to three sentences stating what was done.</section>
        <section name="changes">Bulleted list of file:line changes.</section>
        <section name="verification">Commands run and results.</section>
        <section name="next_steps">Numbered list of follow-ups.</section>
      </output_schema>
    </example>
  </pattern>
</prompt_engineering_patterns>

<tool_orchestration_patterns>
  <overview>
    Complex tasks require sequences of tool calls. Orchestration patterns make these sequences reliable, recoverable, and debuggable.
  </overview>

  <pattern name="sequential_dependencies">
    <description>When tool B depends on the output of tool A, call them sequentially. Never parallelize dependent calls.</description>
    <example>
      <tool-use name="Read">
        <args>
          <arg name="filePath">src/config/config.ts</arg>
        </args>
      </tool-use>
      <result>Returns file content with imports.</result>
      <tool-use name="Grep">
        <args>
          <arg name="pattern">import.*from.*'@/util'</arg>
          <arg name="path">src/config/</arg>
        </args>
      </tool-use>
    </example>
  </pattern>

  <pattern name="fan_out_fan_in">
    <description>When multiple independent reads are needed, parallelize them. Collect results, then decide next steps.</description>
    <example>
      <tool-use name="Read">
        <args>
          <arg name="filePath">src/services/process.ts</arg>
        </args>
      </tool-use>
      <tool-use name="Read">
        <args>
          <arg name="filePath">src/config/config.ts</arg>
        </args>
      </tool-use>
      <tool-use name="Read">
        <args>
          <arg name="filePath">src/mcp/index.ts</arg>
        </args>
      </tool-use>
      <result>Three file contents returned in parallel.</result>
      <decision>Synthesize findings and plan edits.</decision>
    </example>
  </pattern>

  <pattern name="explore_then_act">
    <description>For unfamiliar codebases, explore broadly before acting. Use Task tool for exploration, then narrow with targeted reads.</description>
    <example>
      <step>Use Task tool to find all session-related files.</step>
      <step>Read the most relevant 2-3 files to understand the pattern.</step>
      <step>Form a hypothesis about where to make the change.</step>
      <step>Read the exact target file and surrounding context.</step>
      <step>Make the edit.</step>
    </example>
  </pattern>

  <pattern name="verify_after_act">
    <description>After every edit, verify the result. Read the file at the edit location to confirm the change took effect.</description>
    <example>
      <tool-use name="Edit">
        <args>
          <arg name="filePath">src/services/process.ts</arg>
          <arg name="oldString">const result = data.items[0].value;</arg>
          <arg name="newString">const result = data.items.at(0)?.value ?? null;</arg>
        </args>
      </tool-use>
      <tool-use name="Read">
        <args>
          <arg name="filePath">src/services/process.ts</arg>
          <arg name="limit">5</arg>
          <arg name="offset">710</arg>
        </args>
      </tool-use>
      <result>Confirms the change is in place.</result>
    </example>
  </pattern>

  <pattern name="error_recovery">
    <description>When a tool call fails, diagnose before retrying. Understand the failure mode before attempting recovery.</description>
    <example>
      <tool-use name="Read">
        <args>
          <arg name="filePath">nonexistent.ts</arg>
        </args>
      </tool-use>
      <result>Error: file not found.</result>
      <analysis>The file does not exist. I need to find the correct path. Let me use Glob to search for it.</analysis>
      <tool-use name="Glob">
        <args>
          <arg name="pattern">**/nonexistent.ts</pattern>
        </args>
      </tool-use>
    </example>
  </pattern>
</tool_orchestration_patterns>

<code_style_enforcement>
  <overview>
    Code style is not cosmetic. Consistent style reduces cognitive load, prevents bugs, and makes code review faster. Follow existing conventions before introducing new ones.
  </overview>

  <naming>
    <rule>Use single word names by default for new locals, params, and helper functions.</rule>
    <rule>Multi-word names are allowed only when a single word would be unclear or ambiguous.</rule>
    <rule>Do not introduce new camelCase compounds when a short single-word alternative is clear.</rule>
    <good_examples>
      <example>pid, cfg, err, opts, dir, root, child, state, timeout</example>
    </good_examples>
    <bad_examples>
      <example>inputPID, existingClient, connectTimeout, workerPath</example>
    </bad_examples>
  </naming>

  <control_flow>
    <rule>Prefer early returns over `else`. After an `if` that returns or throws, the `else` is redundant.</rule>
    <rule>Prefer `const`. Replace `let` + if/else assignment with a ternary or an IIFE.</rule>
    <rule>Never leave a `catch` block empty. Log the error or rethrow it.</rule>
    <example>
      <bad>
        <code language="typescript">if (err) {
          throw err;
        } else {
          return data;
        }</code>
      </bad>
      <good>
        <code language="typescript">if (err) throw err;
        return data;</code>
      </good>
    </example>
  </control_flow>

  <type_discipline>
    <rule>Use Zod schemas for input validation on exported functions. Follow the `fn(schema, callback)` pattern.</rule>
    <rule>Prefer type inference when possible. Avoid explicit type annotations or interfaces unless necessary for exports or clarity.</rule>
    <rule>Never use the `any` type.</rule>
    <rule>Avoid possibly out-of-bounds array access. Use `array.at(index) ?? {}` instead of `array[index] ?? {}`.</rule>
  </type_discipline>

  <import_ordering>
    <rule>Follow existing import ordering in the file. Do not introduce a new convention.</rule>
    <rule>Group imports: external packages first, then internal aliases, then relative imports.</rule>
    <rule>Use `@/*` for `./src/*` and `@tui/*` for `./src/cli/cmd/tui/*`.</rule>
  </import_ordering>

  <comments>
    <rule>IMPORTANT: DO NOT ADD ANY COMMENTS unless asked. Comments are noise by default.</rule>
    <rule>The code should be self-documenting. If you need a comment to explain what the code does, rename the function or variable instead.</rule>
  </comments>
</code_style_enforcement>

<refactoring_patterns_detailed>
  <pattern name="extract_class">
    <description>When a class has multiple responsibilities, extract the secondary responsibility into a new class.</description>
    <example>
      <before>
        <code language="typescript">class SessionManager {
          validate() { ... }
          save() { ... }
          notify() { ... }
          log() { ... }
        }</code>
      </before>
      <after>
        <code language="typescript">class SessionManager {
          constructor(private validator: Validator, private repository: Repository, private notifier: Notifier, private logger: Logger) {}
          validate() { this.validator.validate(); }
          save() { this.repository.save(); }
          notify() { this.notifier.notify(); }
          log() { this.logger.log(); }
        }</code>
      </after>
    </example>
  </pattern>

  <pattern name="replace_conditional_with_polymorphism">
    <description>When a function has a complex conditional based on type, replace it with polymorphic dispatch.</description>
    <example>
      <before>
        <code language="typescript">function process(input: Session | Snapshot) {
          if (input.type === 'session') { ... }
          else if (input.type === 'snapshot') { ... }
        }</code>
      </before>
      <after>
        <code language="typescript">interface Session { process(): void }
        class SessionImpl implements Session { process() { ... } }
        class SnapshotImpl implements Session { process() { ... } }
        function process(input: Session) { input.process(); }</code>
      </after>
    </example>
  </pattern>

  <pattern name="introduce_parameter_object">
    <description>When a function has too many parameters, group related parameters into an object.</description>
    <example>
      <before>
        <code language="typescript">function createSession(name: string, model: string, provider: string, timeout: number, retries: number) { ... }</code>
      </before>
      <after>
        <code language="typescript">interface SessionConfig { name: string; model: string; provider: string; timeout: number; retries: number; }
        function createSession(config: SessionConfig) { ... }</code>
      </after>
    </example>
  </pattern>
</refactoring_patterns_detailed>

<scalability_patterns_detailed>
  <pattern name="horizontal_scaling">
    <description>Add more machines instead of making existing machines faster.</description>
    <rule>Design services to be stateless. Store state in external systems (database, cache, object store).</rule>
    <rule>Use load balancers to distribute traffic across instances.</rule>
    <rule>Scale based on queue depth or request rate, not CPU utilization.</rule>
  </pattern>

  <pattern name="caching">
    <description>Store frequently accessed data in fast storage to reduce load on slower backends.</description>
    <rule>Cache at multiple layers: CDN for static assets, application cache for computed data, database cache for query results.</rule>
    <rule>Define cache invalidation strategies explicitly. Stale data is worse than slow data when it is wrong.</rule>
    <rule>Use cache-aside or write-through patterns. Avoid cache stampedes on popular keys.</rule>
  </pattern>

  <pattern name="rate_limiting">
    <description>Limit request rates to protect downstream services from overload.</description>
    <rule>Implement rate limiting at the API layer and at service-to-service boundaries.</rule>
    <rule>Return 429 with a Retry-After header when limits are exceeded.</rule>
    <rule>Use token bucket or sliding window algorithms. Do not use fixed windows for bursty traffic.</rule>
  </pattern>

  <pattern name="sharding">
    <description>Partition data across multiple instances to reduce per-instance load.</description>
    <rule>Choose a shard key that distributes traffic evenly.</rule>
    <rule>Avoid cross-shard queries. They are expensive and fragile.</rule>
    <rule>Plan for re-sharding when a single shard becomes a bottleneck.</rule>
  </pattern>
</scalability_patterns_detailed>

  <case_study name="database_connection_pool_exhaustion">
    <scenario>Production reports "Connection pool exhausted" errors under load.</scenario>
    <investigation>
      <step>Check metrics: connection pool utilization is at 100%.</step>
      <step>Read connection pool configuration: maxConnections = 10.</step>
      <step>Identify that queries are not releasing connections back to the pool.</step>
      <step>Find that a missing `finally` block leaves connections open on error paths.</step>
    </investigation>
    <root_cause>
      Database connections are acquired in a try block but not released in a finally block. When an error occurs, the connection remains open, eventually exhausting the pool.
    </root_cause>
    <fix>
      <code language="typescript">async function query(sql: string, params: any[]) {
        const conn = await pool.connect();
        try {
          return await conn.query(sql, params);
        } finally {
          conn.release();
        }
      }</code>
    </fix>
    <verification>
      Load test with 100 concurrent requests. Confirm pool utilization stays below 50%. Monitor for 1 hour in staging.
    </verification>
  </case_study>

  <case_study name="memory_leak_in_session_snapshot">
    <scenario>The CLI process memory grows indefinitely during long sessions.</scenario>
    <investigation>
      <step>Profile memory with Bun's built-in profiler.</step>
      <step>Identify that session snapshots are stored in an unbounded array.</step>
      <step>Confirm that snapshots are never pruned.</step>
    </investigation>
    <root_cause>
      The snapshot array grows without bound. Each snapshot holds a full copy of session state. Over a 24-hour session, this consumes gigabytes of memory.
    </root_cause>
    <fix>
      Implement a ring buffer with a maximum size of 100 snapshots. When the buffer is full, overwrite the oldest snapshot.
      <code language="typescript">class SnapshotBuffer {
        private buffer: SessionSnapshot[] = new Array(100);
        private index = 0;
        add(snapshot: SessionSnapshot) {
          this.buffer[this.index] = snapshot;
          this.index = (this.index + 1) % 100;
        }
      }</code>
    </fix>
  </case_study>

<architecture_case_studies>
  <case_study name="session_isolation_redesign">
    <problem>
      Session state is shared across all worktree contexts, causing data leakage between worktrees when using Agent Manager.
    </problem>
    <analysis>
      <finding>The current implementation uses a single Snapshot service for all contexts. Directory-keyed InstanceState is not being used for session data.</finding>
      <constraint>The change must be backwards compatible with existing sessions.</constraint>
      <constraint>The change must not break the shared backend architecture.</constraint>
    </analysis>
    <decision>
      Introduce a directory-keyed session store. Each worktree gets its own isolated session namespace. The Snapshot service remains shared for UI state, but session data moves to InstanceState.
    </decision>
    <consequences>
      <positive>Worktree sessions are fully isolated.</positive>
      <positive>Existing sessions continue to work with a migration path.</positive>
      <negative>Increased memory usage due to duplicated state.</negative>
      <negative>More complex session lookup logic.</negative>
    </consequences>
    <alternatives_considered>
      <alternative>Keep shared state and add a worktree prefix. Rejected because it does not solve data leakage.</alternative>
      <alternative>Start a separate backend per worktree. Rejected because it duplicates infrastructure.</alternative>
    </alternatives_considered>
  </case_study>

  <case_study name="tool_registry_refactor">
    <problem>
      Tools are registered in a flat array with string IDs. Adding new tools requires modifying a central registry, violating open-closed principle.
    </problem>
    <analysis>
      <finding>The registry is a hand-maintained switch statement. Every new tool requires a PR that touches this file.</finding>
      <constraint>The change must not break existing tool invocations.</constraint>
      <constraint>The change must support dynamic tool loading from plugins.</constraint>
    </analysis>
    <decision>
      Replace the flat registry with a plugin-based discovery system. Tools register themselves via a decorator or init function. The registry scans for registrations at startup.
    </decision>
    <implementation>
      <code language="typescript">// Before: flat registry
      const tools = [ReadTool, EditTool, WriteTool];

      // After: self-registering tools
      class ToolRegistry {
        private tools = new Map<string, Tool>();
        register(tool: Tool) {
          this.tools.set(tool.id, tool);
        }
        get(id: string) {
          return this.tools.get(id);
        }
      }
      const registry = new ToolRegistry();
      registry.register(new ReadTool());
      registry.register(new EditTool());</code>
    </implementation>
  </case_study>
